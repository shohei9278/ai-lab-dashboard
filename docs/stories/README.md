# 話の種（note の記事の材料）

運営者が書く note の記事は、1本に1つの話（テーマ）にする（運営者が決めた）。
その材料になりそうな出来事を、ここに1件1ファイルで貯める。記事の下書きを書くルーティン（zenn-articles の `docs/routine-article-draft.md`）が毎朝読み、まだ使っていない話から1つ選んで書く。選ぶときの関門は次の2つ（11/27 に運営者が決めた）。2つともそろう話がなければ、その日は note を書かない
1. 読み終えた人が、明日1つ変えられることを1文で書ける
2. それが常識（AIを使わなくても誰でも分かること）ではなく、AIと一緒に仕事をして初めて分かったこと（例: 「見られた数より、使われた数を見る」は宣伝の常識なので当たらない。「プロンプトに決まりを足しても、同じことに触れる前の行が残っていると効かないことがある」は当たる）

読む人は、AIで開発しているエンジニアや、ITを勉強している人でよい（運営者が決めた。AIに興味のある人は、エンジニアが多いため）

## 貯めるとき
- ai-lab の作業（Claude Code とのやり取り）で、話になりそうな出来事があったら、その作業の PR に1ファイル足す（決まりは `CLAUDE.md`）
- ファイル名: `docs/stories/YYYY-MM-DD-<英小文字とハイフン>.md`（出来事の日付。日本時間）
- 話になりそうな出来事の目安（どれか1つに当たればよい）
  - 人が直す必要があった・思ったように効かなかった（足した決まりが効かなかった、直したら別の所が困った など。記事の関門の2に、いちばん当たりやすい）
  - AI が、数字や結果を見て、自分で判断を変えた（人が先に指示に書いていたことではないかを、指示を読んで確かめる）
  - AI の仕組みが、思わぬ所で止まった・間違えた（AI だけで立て直したもの・原因がまだ分からないものも入れる。人が何かしたときは、それも書く）
  - AI どうしで意見が割れた・AI と人の判断が違った
  - 数字がはっきり動いた（良くても悪くても）
  - 人の出番がはっきり変わった（人がしていたことを AI に任せた・任せていたことを人に戻した）
- 小さな直しの一覧や、仕組みの説明だけのものは種にしない（それは PR と改善の記録で足りる）

## 書き方（事実だけ・短く）
```markdown
# 題（その話を一言で）

- 日付: 2026-11-26
- 関わるもの: PR #194・#195、本番の「毎日の計画」など

## 起きたこと
（何が起きたか。時刻・数字は記録にあるものだけ）

## AIに渡していた指示・人が先に決めていたこと
（関わるAIに、出来事の時点で渡っていた指示を読んで書く。朝の計画なら `src/lib/plan.ts`、会議なら `src/lib/meeting.ts` など。出来事のあとに指示が変わっていることがあるので、その日のコミットの版（`git log --until=<その日時> -1 -- <ファイル>` と `git show <コミット>:<ファイル>`）を読む。人が先に指示に書いていた物差し・上限・優先する順。なければ「なし（〇〇のその日の版を読んで確かめた）」。確かめられなかったときは「なし」と書かず「確認できていない」と書く。PR #216 の ai-review の指摘）

## 思ったのと違った所
（なぜ話になるのか。思ったように効かなかった・逆になった・ぶつかった所。AI がどう考えて動いたか）

## 人がしたこと・言ったこと
（運営者が実際に言ったこと・決めたことだけ。言っていない判断は書かない。同じ出来事の改善の記録 `src/data/interventions/` があれば、そのファイルの名前も書く）

## どうなったか
（結果。数字は日付つき。まだ分からなければ、そう書く）

## まだ分からないこと

## AIと仕事をして分かった、明日変えられること
（読む人が取る行動だけを1文で。根拠や、記事の芯にしない話は、前の欄に書く。常識で分かることなら「なし」と書き、理由を一言）
- 読む人: （AIで開発しているエンジニア・ITを勉強している人・AIを使い始めた人 のどれか）
```
- 話の種には、感想・気持ちを書かない（事実と、運営者が実際に言ったこと・決めたことだけ）。「明日変えられること」は、事実から言えることだけを書く（確かめていない効き目を言い切らない）
- 「AIが自分で決めた」と書く前に、出来事の時点の関わる指示を読む（11/26 の種に、人が指示に書いていた物差しを「AIだけで決めた」と書き、記事でもAIの気づきとして書かれたため）
- 記事のほうでは、運営者の声の所に、話の種や改善の記録にある運営者の言葉・決めたことをもとに、たたき台を【あなたの声の下書き（直してから使う）: …】として書く。運営者が直して使う（決まりは zenn-articles の `docs/routine-article-draft.md`）
- 起きたことと、そこから言えることを分ける。確かめていない原因・効き目は言い切らず、「まだ分からないこと」に書く
- 秘密の値・個人の情報・来訪者に見せていない下書きや AI の入出力は書かない。運営者の名前は書かず「運営者」と書く
- 記事に使われたかは、記事の下書き（zenn-articles の `note/`）の先頭のコメントの「使った話の種」でわかる。ここのファイルは消さない
