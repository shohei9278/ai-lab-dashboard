# AIが作れるものの縛りを見直す（設計）

11/28 に運営者が、「ブラウザで動く小さなツール」という縛りは嫌なので、縛りを全部見直したいと言い、まず設計の文書から書くと決めた。
この文書は、何をどの順で広げるか、広げても何を守るかを決めるためのもの。作るのは、ここで決めたあとに1段ずつ別の PR で行う。

## これまでの経緯
- 11/17 に、「じっくり案件」の第1段（大きなデータ・人が入れる素材・見た目を磨く段）を作った。第2段（外部の API を許す）は、AIがどんな API をどれだけ欲しがるか分からないので、入口だけ作った（`src/lib/apiWishes.ts`。AIが書いた「使いたい API」を数える）
- アイデアには「要るもの（needs）」も書ける（`src/lib/needs.ts`）。保存の場所・外部の API・その場で AI を呼ぶ、は「まだない仕組み」で、そう書いた案件は「人の作業待ち」で止まる（`needsWaitMax` 件たまると、そういう案件は新しく作らない）
- 同じものが何度も欲しがられたら、AIが使えるサービスを調べ、定例会議で運営者に契約を頼めるようにした（`src/lib/wants.ts`）。契約したあと、ツールからつなぐ部分（共有の保存・外部の API の中継）は、運営者が後回しにしていた
- 11/28 から、Claude Code につながっているときは、ツールは全部じっくり案件として、クラウドの Claude Code がブラウザで確かめながら作る

## 広げても変えないこと
- 秘密の値（API キー・トークン）は、ツールにも、ツールのコードにも、ブラウザにも渡さない。Vercel・Railway の変数にだけ置く
- ツールの枠は隔離したままにする。allow-same-origin は付けない。CSP で外への通信を広く開けない
- 訪問者の情報を、外に送るときは、送り先と送るものをプライバシーポリシーに書いてから送る。運営者が承認していない送り先には送らない
- お金がかかるものは、サーバーの側で1日の上限と1人の回数を決め、緊急停止（`killSwitch`）と月の予算（`monthlyBudgetJpy`）で止まるようにする
- 訪問・利用・シェアの数え方は、どの出し方でも、今と比べられる形にする
- AIだけで公開できる範囲は、新しい仕組みごとに決める。決めるまでは、新しい仕組みを使うツールは人の承認に回す

## 共通の作り: 窓口を足す
①〜③ は、どれも同じ作りで足す。ツールが外と直接やり取りするのではなく、今の `window.labStore` と同じように、ページの側の窓口にお願いし、Hitoride のサーバー（Vercel）が代わりに行う。

```
ツール（隔離された枠） --postMessage--> ページ（ToolFrame） --> Hitoride のサーバー（/api/tool-…） --> Supabase・外部の API・AI
```

- ツールの CSP は今のまま（通信できないまま）にできる。鍵は Hitoride のサーバーにだけある
- 窓口は、案件ごとに「使ってよい」と決めたものだけ開く。公開の中身（Supabase の `lps.content`）に、使える窓口の一覧を入れ、ページとサーバーの両方が見る
- 機械のチェック（`staticToolIssues`）は、「使ってよいと決めた窓口以外を使っていないか」を見る形に変える
- 窓口を作るときに、`needs.ts` のその種類の `ready` を true にし、ツールを作るときの決まり（`toolRules`）も一緒に直す（`needs.ts` の注に書いてあるとおり）
- 公開中の今の版のツールからの呼び出しだけを受け付ける（`/api/event` と同じ確かめ方）

## ① みんなで共有する保存
- できること: 投票・みんなの結果の割合・ランキング・「あなたは○人目」
- 作り: `window.labShared`（仮の名前）。Supabase に、ツールごとの数を数える表を足す
- 最初は、数と、決めた選択肢だけを保存する。訪問者が書いた自由な文は保存しない（ほかの人に見えると、荒らしや個人情報が出る）
  - 自由な文を見せたくなったら、別の段で決める（AI の確かめ・通報・消す手立てが要る）
- 1人が何度も入れられないよう、訪問者の番号（今の `visitorId`）ごとに回数を決める。数が小さいうちは、少ない数の割合を大きく見せない
- プライバシーポリシーに、ツールで選んだものを保存することを書く

## ② 外部の API
- できること: 天気・地図・祝日・翻訳など
- 作り: `window.labApi`（仮の名前）。運営者が承認した API の一覧を持ち、Hitoride のサーバーが代わりに呼ぶ。ツールは一覧の名前と決めた引数だけを渡せる
- 一覧の1件ごとに、呼ぶ先・送ってよい引数・鍵の変数の名前・1日の回数・結果をためておく時間・送る情報を書く。鍵の値は書かない
- 最初は、鍵が要らず、訪問者の情報を送らない API から始める
- どれを一覧に入れるかは、`apiWishes.ts` が数えた「使いたい API」の多い順を材料に、運営者が決める
- 送り先ができるので、プライバシーポリシーに API ごとの送り先と送るものを書く

## ③ その場で AI を呼ぶ
- できること: 訪問者の入力に AI が答える・名前を付ける・診断の文を書く・絵を描く
- 作り: `window.labAi`（仮の名前）。Hitoride のサーバーが AI を呼ぶ
- AIへの指示（どう答えるか）は、ツールのコードに書かせず、案件ごとに決めて、公開の前に人かチェックが確かめたものに固定する。ツールから渡せるのは、訪問者の入力（長さの上限あり）と決めた選択肢だけにする
- お金の上限: 全体の1日の上限（円）・1人の1日の回数・1回の長さを決める。上限に届いたら、ツールは「今日はここまで」と出し、AI なしで遊べる作りにさせる。月の予算と緊急停止でも止まる
- 出てきた文が、ほかの人に見せられない内容になっていないかを確かめてから返す
- 訪問者の入力と AI の答えは、最初は保存しない（数だけ数える）。直すために読みたくなったら、別の段で決める
- 結果の画面に、AI が書いたものだと分かる一言を出す
- AI に送ることを、プライバシーポリシーに書く

## ④ 出し方を足す
今の LP とツールのほかの出し方。重いものほど人の作業が増え、AI だけで回る部分が減る。

| 出し方 | 人の作業 | 数え方 | 重さ |
| --- | --- | --- | --- |
| ホームに置けるアプリ（PWA） | ほぼなし。Hitoride に置き方を足すだけ | 今と同じ（Web） | 軽い |
| 画像・動画そのものを作品にする | 投稿は今と同じ | SNS の数 | 軽い〜中 |
| Discord・LINE の bot | アカウント作り・審査・鍵の用意 | bot の側で作り直す | 中 |
| Chrome 拡張・スマホのアプリ | ストアの登録・審査・料金 | ストアの数を手で入れる | 重い |

- 最初は PWA だけを足し、ほかは、AI が会議でそれを欲しがったら（`wants.ts` の欲しい仕組みとして数える）、運営者が決める
- アイデアの形（kind）を増やすのは、出し方を1つ足すときに一緒に行う（kind を先に増やすと、作れない案が出る）

## ⑤ 大きさ
- HTML の断片1つ・長さの上限は、①〜④を入れるときに、足りなくなったぶんだけ広げる。先には変えない

## 順番
1. 共通の作り（窓口の一覧・チェックの直し）を ③ と一緒に作る
2. ③ その場で AI（面白さへの効き目が一番大きい。上限を決めれば危なさを抑えられる）
3. ① みんなで共有する保存
4. ④ の PWA
5. ② 外部の API（`apiWishes.ts` で、同じ API が何度も欲しがられてから）

「人の作業待ち」で止まっている案件の種類の数を見て、多いものを先にしてよい。

1段ずつ別の PR にする。どの段も、出したあとに、その仕組みを使ったツールを1件公開して、数字（使った人の割合・シェア）と費用を見てから次に進む。

## 運営者に決めてもらうこと
- 順番（上のとおりでよいか）
- ③ の全体の1日の上限（円）と、1人の1日の回数
- ③ を使うツールを、AI だけで公開してよいか（最初は人の承認に回す案）
- ① で、自由な文を見せる段に進むか（最初は進まない案）
- ④ で、PWA のほかに足したい出し方があるか
